# v0.8.0 scheduler wait gate

## Root cause

Goal Guardrails 0.7.0 could tell a no-event activation to stop, but the Codex Goal runtime created that activation before the SessionStart hook ran. Even a short "still waiting" response therefore spent provider tokens and entered the thread context. The terminal monitor could already wake the exact thread, so periodic Goal continuation had no useful role while an external job was running.

Codex 0.151 already persists a per-thread Goal continuation deferral for forked threads and checks it before creating an idle turn. It clears that marker at the start of an explicit turn. The companion runtime patch exposes that existing primitive through experimental, expected-Goal-ID App Server methods; it does not add another scheduler, Goal status, or database table.

The patched executable can be installed as a versioned App Server sidecar for the monitor bridge; it does not need to replace the user's normal `codex` command. The ordinary Codex 0.151 process already performs the persisted marker check. Both processes must use the same frozen `CODEX_HOME`, and the bridge config/lifecycle receipt must pin the sidecar's absolute path and digest.

The cross-process ordering invariant is explicit: initial `wait-monitor` runs synchronously as a tool inside the target thread's current turn, and re-arm runs synchronously inside that thread's SessionStart hook. The controller does not return from either call until sidecar set + read-back succeeds. The primary runtime therefore cannot reach `on_thread_idle` before the durable marker exists. Do not arm v2 from an unrelated shell or after the target turn has already ended; such a call is outside the supported zero-turn contract.

## State transitions

| Event | v0.7.0 | v0.8.0 contract v2 |
|---|---|---|
| monitor run frozen | directly suspend lease | suspend the lease clock and persist `ARMING_EXTERNAL_WAIT` |
| continuation arm/read-back succeeds | unavailable | suspend lease and enter `WAITING_EXTERNAL_EVENT` |
| arm transport/process fails | could still rely on behavioral wait | remain ARMING; retry the same binding, never resubmit |
| Goal idle while waiting | model continuation turn may be created | persisted marker prevents turn creation |
| explicit no-event SessionStart | model receives an end-wait instruction | re-arm/read-back, then `continue:false` before provider request |
| terminal exact-thread wake | controller consumes event | Codex clears marker at turn start; controller consumes event once |
| duplicate event | no-op | no-op |

The controller stores the verified scheduler-gate record in both the active lease and runtime wait record. It binds the lease, monitor, frozen Job ID, monitor run, thread, active Goal ID, bridge config/event binding, Codex executable, executable digest, and project-external receipt digest. `WAITING_EXTERNAL_EVENT` is not committed until the bridge reports `deferred=true` for the same active Goal and the receipt is independently read from the frozen monitor state root.

The SessionStart hook budget is longer than the bounded bridge subprocess budget. If re-arm still fails, the controller retains the same suspended lease and emits a recoverable scheduler error instead of changing the experiment result or submitting another Job.

## App Server contract

The patched Codex 0.151 App Server exposes experimental:

- `thread/goal/continuation/get {threadId}`
- `thread/goal/continuation/set {threadId, expectedGoalId}`
- `thread/goal/continuation/clear {threadId, expectedGoalId}`

Responses contain only `goalId`, `status`, and `deferred`. Set and clear reject a missing, replaced, or non-active expected Goal. The monitor bridge uses get → set → get read-back and never calls `turn/start` on the arm path. Clear is a pure conditional marker update and does not start Goal continuation; an explicit resume/wake turn remains responsible for forward progress.

## Compatibility and migration

- `CONTROL.json` remains schema 1. `ARMING_EXTERNAL_WAIT` and scheduler-gate records are additive.
- Existing external-monitor contract v1 remains accepted and behaves exactly as before. It is the compatibility path for an already-admitted or already-running workload.
- Contract v2 is opt-in for new proposals and requires regular sibling `supervise_slurm_job.py` and `app_server_bridge.py` files, an absolute event binding and bridge config, `--bridge-service-name`, and `--require-auto-resume`.
- The bridge must pin the patched Codex 0.151 absolute executable and SHA, and its lifecycle receipt must match that binary.
- Upgrading does not requeue, cancel, or resubmit a Job. A v2 arm failure is recovered by repeating `wait-monitor`, not submission.
- Stock Codex or unsupported versions may continue using v1, but v1 does not guarantee zero Goal turns while waiting.

## Failure boundary

Continuation transport failure is scheduler recovery, not an experiment result and not a business pause. The Goal remains associated with the same active lease and chain. The controller may request human input only if the exact-thread binding or required runtime itself is unavailable and autonomous recovery cannot restore it; it must never convert the missing marker into a duplicate submission or a fabricated terminal result.
